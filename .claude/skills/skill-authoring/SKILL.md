name: skill-authoring
description: Create new skills and iteratively improve existing ones. Use whenever the work touches a skill at all — creating one from scratch, editing, refining, trimming, or splitting an existing skill, testing a skill against realistic prompts, or sharpening a `description:` so it triggers reliably. Fires on any edit under `.claude/skills/` or to a `SKILL.md`, even when the user doesn't say "skill".
---

* skill-authoring: makes you better at creating a new skill and improving an existing one — knowing what belongs in a skill, how skills load and trigger, and how to test one.

* Rules
  * The shape is fixed — every skill you write or edit, including this one, has its body in the three-part shape (definition, Rules, Steps) defined in [`references/skill-structure.md`](references/skill-structure.md), which you read before writing and match exactly.
  * Rule of thumb for what goes where — a skill *teaches* you something, a reference *defines one thing*, a script *runs deterministically*, so the rules and step-by-step guide stay in the SKILL.md, illustrations and worked examples move to `references/`, and anything executed verbatim belongs in `scripts/`.
  * Manage skills exactly like reusable code — isolated units, a clear API, no leaked internals — and this outranks every style preference below, because duplication across skills drifts like copy-pasted code with nothing to type-check it.
  * One owner per concern — exactly one skill defines a given topic, rule, law, or convention; if it's already owned, extend that skill and reference it by name rather than writing a second that covers part of it, and when a rule has no home yet but several skills need it, create the canonical skill first then wire the references (as `plain-english` did for the jargon-free law and `frontend-ui-architecture` for UI placement); length is never a reason to split — only a *different concern* is.
  * Consumers call by name and nothing more — a skill that invokes another names it and states what it's for, and must not restate the callee's steps, commands, thresholds, tool mechanics, vocabulary, or history, so that when the callee changes no consumer needs editing.
  * No private helper promoted to public API — if a skill exists only to be run by one other skill, it isn't a skill but a section of that skill, so fold it in.
  * A cross-reference is one clause — "run the `X` skill" or "see `X` for Y" — and the moment a reference starts explaining *how* X works, the boundary has leaked.
  * When editing a skill, grep the other skills for its name and confirm every hit is still a name-only mention, since stale restatements are the failure mode these module rules exist to prevent.
  * Write only what the agent can't work out at runtime — before any line ask "would I get this right without being told?", and cut the three shapes of noise: the obvious (mechanics the agent knows cold and steps a competent agent supplies unaided, which also drift as inlined detail goes stale), the restatement (saying a fact more than once instead of stating it once where it belongs, keeping only the tiny core of conditions and definitions the agent can't infer), and the leaked mechanic (anything about a tool a reference owns — even its *name* — which must route through the pointer, "read X per `references/foo.md`", rather than be copied).
  * Reserve explicit literal detail for the three cases the agent can't be trusted to get right unaided: non-obvious (a step no reasonable agent would infer, a surprising ordering or subtle precondition), repo-specific (a name, flag, or convention that only holds here and can't be guessed — but not a path used to say where something lives), and destructive-if-wrong (where a wrong guess loses work or ships something bad, so pinning down the exact form earns its space).
  * The one exception runs the other way — code that executes without the agent in the loop must be a literal, checkable script rather than intent (a detached background poll like the one `wait-for-pr-merge` externalizes has no agent present to fill in the mechanics): run *by* the agent means intent is enough, run *detached* means write the script.
  * Keep repo paths outside the skill — name locations by concept ("the shared core package", "the Hasura metadata") not by path, since a path is the first thing a refactor breaks and the current one is always discoverable from the code; the only paths that stay are a pointer to a `references/` fact-file and the path slot an example command needs (`docker build -f <dockerfile> .`).
  * Keep private values outside the skill — this is a public repo, so state the *mechanism* (which keys exist, that a flag overrides a default) never the *values* (user IDs, account names, secrets, which stay in local config and memory), use a placeholder, and scan the diff for real IDs, handles, and tokens before finishing.
  * Write imperatively and explain the *why* rather than leaning on heavy-handed MUSTs — given the reasoning the model goes beyond rote compliance, and all-caps ALWAYS/NEVER is a yellow flag to reframe and give the reason.
  * Keep examples evergreen — an example illustrates a rule and must not tie the skill to volatile state, so use no real ticket or PR numbers, dated URLs, or live record IDs (the moment that record moves the example misleads the next reader) and pick a generic scenario that still reads true a year from now.
  * A skill's contents must not surprise the user given its stated intent — no malware, exploit code, or anything built to facilitate unauthorized access or data exfiltration (harmless things like "roleplay as an X" are fine).
  * Put each thing at the load level where it's needed — metadata (name + description) is always in context, the SKILL.md body loads whenever the skill triggers (aim under ~500 lines, adding hierarchy with clear pointers if you're near it), and bundled resources pull in only as needed (scripts can execute *without* being loaded); give reference files over ~300 lines a table of contents, make sure anything bundled actually ships alongside the SKILL.md or it fails at runtime, and when a skill spans several domains split by variant (e.g. `references/{aws,gcp,azure}.md`) so only the relevant file loads.
    * directory layout and load levels: [`references/authoring-notes.md`](references/authoring-notes.md)
  * The description is the sole trigger — Claude picks a skill from its name + description alone, so every *what it does* and *when to reach for it* cue lives there not in the body, and since Claude tends to undertrigger make it a little pushy; a trivial one-step task may not trigger a skill even with a perfect description (Claude reaches for skills on work it can't easily handle directly), so don't chase the un-catchable.
    * pushy-description example: [`references/authoring-notes.md`](references/authoring-notes.md)
  * Test a skill when its outputs are verifiable (file transforms, extraction, codegen, fixed workflow steps) and skip testing for taste/style skills where there's nothing objective to compare.

* Steps
  * Meet the user where they already are and jump in there — straight to testing if they have a draft, skip the evals if they ask to.
  1. Gather the three things only the user can give — what the skill lets you do and when it fires (this becomes the `description`), the repo-specific facts it must encode that you can't discover (a name, flag, value, or non-obvious ordering), and whether it should be tested or is a taste/style skill where evals don't help.
  2. Draft the skill in the fixed three-part shape.
  3. Pressure-test the `description` with a handful of realistic queries — a mix of *should-trigger* and *should-not-trigger* near-misses that share keywords but need something different (the ambiguous cases are the valuable ones), refining until it catches the real cases and leaves the near-misses alone.
  4. Test with-skill against a baseline in two subagents run the same turn — write 2-3 prompts a real user would actually say and confirm them with the user, give one subagent the skill and the task and the other the same prompt with no skill (or a `cp -r` snapshot of the old version when improving one), then read the transcripts not just the final outputs to see what the skill actually *changes*, generalising from the feedback rather than overfitting and bundling into `scripts/` any helper every run reinvented.
